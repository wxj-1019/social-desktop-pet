## 1) Potential bugs

**B1 — Important: external embedding HTTP call happens inside the open transaction (holds a pooled connection up to 8s).**
`recallMemories` runs `begin` (L79), sets RLS claims, then at L114 calls `this.queryEmbedding(input.query)` *while the transaction is open*, and only `commit`s at L133. `createOpenAiCompatibleEmbeddingClient` (embedding.ts L44) uses `AbortSignal.timeout(8_000)` — an embedding provider that is slow or down pins a pooled connection for up to 8s per chat turn. Pool max is 20 (pool.ts L18); a modest burst of concurrent chats during a provider outage exhausts the pool and stalls every chat. This directly contradicts the codebase's own documented pattern: `persistMemory` (L184–185) explicitly generates embeddings **outside** the transaction ("事务内长占连接会拖垮连接池") — `recallMemories` does the opposite.
Fix: hoist `queryEmbedding` before `begin` (mirror L184–194), then open the transaction.

**B2 — Important: `queryEmbedding` has no error handling, so provider failure kills the whole chat turn instead of degrading to FTS-only.**
`embedValue` (L54–64) catches errors and degrades to `null` with a warning; `queryEmbedding` (L47–51) does not. The embedding client throws on network error / 5xx / timeout (embedding.ts L47–50; its own doc says "异常时由调用方兜底" — the caller here doesn't). The throw propagates: `recallMemories` → `retrieveMemoryNodeFactory` (memory-retrieval.ts L168) → graph `invoke` (state-graph.ts L74–111 has no per-node catch) → SSE `error`, so the user gets **no reply** — after usage was already recorded (chat.ts L217) and rate-limit consumed. The FTS-only degradation that AGENTS.md describes as the default mode is broken on the recall path.
Fix: wrap `embed` in try/catch and return `undefined` (skip the vector arm), same as `embedValue`.

**B3 — Minor: interface contract drift — `input.queryEmbedding` and `input.topK` are dead parameters.**
`MemorySearchInput` documents `queryEmbedding` as "由调用方注入；无则服务端跳过向量臂" (memory-retrieval.ts L47–48), but the implementation ignores it and generates its own embedding (L114). `topK` is also never used (hardcoded `RECALL_ARM_LIMIT = 20`). Worse, `retrieveMemoryNodeFactory` calls `recallMemories` even when `retrievalTopKForLevel` returns 0 for L0/SAFETY routes (memory-retrieval.ts L167–173) — paying an 8s-capable embedding call and a 20-row recall for memories that will be discarded. Fix: early-return `{vectorHits:[], ftsHits:[]}` when `topK <= 0`, and either honor `queryEmbedding` or remove it from the interface.

**B4 — Important (functional): the `'simple'` FTS config doesn't tokenize CJK, so the FTS arm is effectively a null arm for this Chinese-language product.**
`to_tsvector('simple', value)` treats a Chinese sentence as a single lexeme; `plainto_tsquery('simple', $4)` requires an exact lexeme match. A query like "喝什么" only matches a memory whose value contains that exact whitespace-delimited token — in practice, nothing. Since AGENTS.md states embeddings are not yet configured in deployments ("未配置密钥时自动降级 FTS-only"), the **shipped default recall path returns ~nothing for natural Chinese queries**. Note `findSimilar` (L160) compensates with `ILIKE '%…%'`, which is why dedupe works but recall doesn't. Consider `pg_trgm` GIN on `value`, or a Chinese-aware tokenizer, or at minimum document the limitation.

**B5 — Minor: nondeterministic ranking in both arms.**
Vector arm orders only by `embedding <=> $4` (L126) — HNSW resolves ties arbitrarily; FTS arm orders only by `ts_rank_cd` (L107). RRF (memory-retrieval.ts L93–111) ranks by position, so tie-breaking jitter changes fused ordering between calls. Fix: add `, updated_at desc` (or `created_at desc`) tiebreakers.

**B6 — Nit: `rollback` in the catch masks the original error if `begin` itself failed (L79/L138–140).** Also a plain `begin` for read-only work; `begin read only` documents intent.

## 2) RLS / permission risks

**R1 — Design note: RLS here is only as strong as the claims-setting code.** Every transaction sets `request.jwt.claims` from the `ownerUserId` argument the app passes (L80–82). RLS cannot distinguish "owner correctly derived from the session" from "caller passed an attacker-influenced id" — it just believes the claims. The boundary holds today: chat.ts takes `userId` from the verified JWT (`payload.sub`, business.ts L82) and hardcodes `scenario: 'private_chat'` (chat.ts L235). But `recallMemories` itself performs no ownership derivation — if a future caller passes a user-controlled `ownerUserId`, the explicit `owner_user_id = $1` filter *and* RLS both pass. Mitigation: keep claims-setting + explicit owner filter (both present — good) and centralize/assert the ownerUserId source. Also note: `is_local=true` (transaction-scoped) is set *after* `begin` (correct order), and no claims leak across pooled connections — good.

**R2 — The `friend_visit` permission path is dead code with zero test coverage.** `visibilityScope`/`sensitivityScope` branches for `friend_visit` (L32–34, L69–71) are unreachable: no caller passes `purpose='friend_visit'` (only chat.ts L235), and no insert path writes `visibility='public_profile'` or `purpose='friend_visit'` — `persistMemory` hardcodes `'private'/'private_chat'` (L206), and the memories.ts edit endpoint preserves old values (L404–405). Consequences: (a) functionally, friend-visit recall always returns zero rows — the "share public memories with a friend" feature silently can't work; (b) security-wise, the two filters that will be the actual security boundary for the friend feature (exclude `high` sensitivity; only `public_profile` visibility) are untested dead code — memory-store.test.ts only exercises `private_chat` and asserts nothing about the filter SQL. When the feature is wired up, this needs tests first.

**R3 — Minor: no CHECK constraints on `visibility`/`purpose` (0001 L127–128).** The recall filter depends on these values; protocol zod validates API input, but `persistMemory` consumes graph (LLM-influenced) output directly. A future insert path writing an unexpected combination (e.g., `purpose='private_chat'` + `visibility='public_profile'`) would silently change recall exposure. Align DB constraints with `MemoryVisibilitySchema`/`MemoryPurposeSchema`.

**R4 — Positive: the permission filter is correctly applied identically to both arms.** The shared `filter` (L85–90) covers owner + `memory_status='active'` + purpose + visibility + sensitivity + time validity (`expires_at`/`valid_from`/`valid_to`) on FTS **and** vector paths; the vector arm adds only `embedding is not null` (L125). Embedding is treated as plaintext-equivalent per the schema comment, and the vector arm does not bypass any filter. Parameterization is complete ($n placeholders throughout; the filter string is a constant — no injection surface).

## 3) Optimization suggestions

- **O1 (biggest win): hoist embedding generation before `begin` and wrap in try/catch** — fixes B1 and B2 simultaneously and mirrors the persistMemory pattern.
- **O2: skip recall when `topK <= 0`** (L0/SAFETY turns) — saves the embedding HTTP call and both queries for nothing (see B3).
- **O3: consider running the two arm queries concurrently** (`Promise.all` over two pooled clients, each with its own transaction + claims) once the embedding is hoisted — roughly halves recall latency; weigh against pool pressure (max 20) and the 8s embedding tail.
- **O4: materialize the tsvector** — a stored/generated `value_tsv` column with the GIN index and `ts_rank` over the column moves the `to_tsvector('simple', value)` parse cost (currently repeated in WHERE/ORDER BY/SELECT on every recall) to write time.
- **O5: for CJK recall, evaluate `pg_trgm` GIN (`gin_trgm_ops`) on `value`** for an ILIKE-based arm or a proper tokenizer (see B4); it also lets the FTS arm reuse the dedupe-style matching that works in `findSimilar`.
- **O6: add deterministic tiebreakers** to both arms (see B5).
- **O7: `begin read only`** — documents read-only intent and is marginally cheaper than a read-write transaction.
- **O8 (tests): strengthen `memory-store.test.ts`** — the scripted client (L20–37) silently skips `set_config` without asserting it, so a regression that drops RLS claims-setting would pass CI. Add: an assertion that `set_config('request.jwt.claims', …)` is issued per transaction with the caller's owner id; tests for provider-failure degradation in recall (B2), the friend_visit scopes (R2), time-validity filtering, and empty-query behavior.

**What's good:** single-sourced permission filter shared by both arms; transaction-scoped claims set after `begin`; graceful FTS-only degradation on the persist path; fully parameterized SQL; sensible fixed recall depth (20) with RRF fusion done in the testable pure function — the overall hybrid-recall architecture (store recalls, graph scores) is clean.

Top priorities: **B1/B2/O1** (transaction-holding embedding call + missing degradation — one fix addresses both, and both are main-path issues), then **B4** (shipped FTS-only mode is near-useless for Chinese), then **R2** (test the friend_visit boundary before wiring the feature).
