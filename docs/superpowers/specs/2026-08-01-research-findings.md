## 二、客户端技术选型（设计稿第 8 章）

### 2.1 🔴 API 命名混淆（事实错误）

文档 8.1 称 Electron 提供"整窗鼠标穿透"，但实际对应 API 名称：

- **Electron**：`win.setIgnoreMouseEvents(ignore, { forward: true })`
- **Tauri 2**：`setIgnoreCursorEvents(ignore)`

文档行文里出现了 Tauri 的命名。需统一修正。

### 2.2 🔴 逐像素穿透不可达，且被低估为产品风险

- Electron 原生**不支持**透明区域点击穿透（官方文档明示 "You cannot click through the transparent area"，issue #1335 至今 Open）。
- 唯一可用方案：`setIgnoreMouseEvents(true,{forward:true})` + 渲染进程 JS 探测光标下 alpha → IPC 切换。**有可观察副作用**：边缘抖动、拖拽经过宠物边缘误判、点击身后窗口需先移开。
- 文档"MVP 只支持整窗穿透切换"在工程上务实，但应在**产品章节**明确标注：**逐像素无感穿透在 Electron 路线不可达**，并据此评估"桌宠常驻不妨碍工作"这个核心卖点在 MVP 阶段的折损程度。

### 2.3 🟠 Tauri 2 备选被高估（文档判断有误）

文档要求 Tauri 2 上"透明窗/穿透/WebView2 透明/签名公证全通过"作为 5 天 PoC 门槛。实际：

- Tauri 2 的 `setIgnoreCursorEvents` **没有 forward 选项** → 无法逐像素穿透（结构性缺口，issue #13070 已关闭）
- WebView2 启动**白屏闪烁**（#5170）
- 子窗口 `transparent` **渲染纯黑**（#12450）

**结论**：对"桌宠"这种强依赖透明+穿透的形态，Tauri 2 是结构性障碍，不是 5 天 PoC 能解决的。文档应改为"Tauri 路线在透明+穿透能力上存在结构性缺口，不做首选预期"。

### 2.4 🟠 Electron 版本必须锁定下限（文档遗漏）

- **Electron ≥42.8.0**：修复 macOS 透明窗被覆盖时被错误 background-throttle（导致桌宠被覆盖时动画暂停）。文档未提，但这是桌宠常驻场景的硬性下限。
- **Electron 43.2.0 起** `setIgnoreMouseEvents` 在 Linux/X11 回归失效（#52456），未修复。MVP 不含 Linux 无影响，但若未来扩展 Linux 是硬阻断。

### 2.5 🟠 性能门槛过于乐观

| 指标                | 文档门槛                                                                 | 评估              |
| ------------------- | ------------------------------------------------------------------------ | ----------------- |
| 空闲 CPU P95 ≤2%    | 带 WebGL 持续渲染的桌宠**非常吃紧**                                      | 建议改 P50 或放宽 |
| 空闲 RSS P95 ≤300MB | Electron 精简 idle ~150MB，但桌宠是**前台常驻+持续渲染**，GPU 进程会抬高 | 建议改 P50 或放宽 |

参考：VPet-Simulator（WPF 原生）官方最低要求 500MB。Electron + WebGL + 持续动画压到 300MB P95 非常困难。

### 2.6 🟠 Live2D 口型方案未定（技术空白）

文档要求"文字对话口型动画"，但**无 TTS 场景下 SDK 本身无文本→口型能力**。必须二选一：

- (a) 预烘焙口型 motion 随文本播放
- (b) MotionSync Plugin（免费、royalty-free，需 Cubism Editor 5.0）

应补充到 PoC 验收清单。

### 2.7 🟡 Godot 排除理由过时

文档说 Godot"无官方 Live2D Godot SDK"。社区方案 **gd_cubism**（支持 Godot 4.3+，GDExtension，被 Live2D 官方 Community SDK 收录）已较成熟。应改为"无官方 SDK，社区 GDExtension 有维护与许可风险"。

### 2.8 🟡 macOS Tahoe (26) 平台风险

macOS 26 有多个透明窗口回归：截图 PNG 不带 alpha、全屏透明 broken、Reduce Transparency 失效、ScreenCaptureKit 行为变化。需补到 PoC 验收。

## 三、Live2D 许可（设计稿 8.8 节）

### 3.1 🔴 许可模型理解不完整（重大遗漏）

文档只提"SDK 许可"，实际 Live2D 商业使用涉及**三套互相独立的许可**：

| 许可                       | 用途                   | 文档是否提及 |
| -------------------------- | ---------------------- | ------------ |
| A. Cubism **Editor** 许可  | 建模/绑骨（美术用）    | ❌ 完全未提  |
| B. Cubism **SDK 发布许可** | 在 App 中运行模型      | ✅ 提及      |
| C. **样本素材**许可        | Kei/Epsilon 等官方示例 | ❌ 完全未提  |

**关键**：

- Editor 与 SDK 许可分开——建模师买 PRO ≠ App 自动获 SDK 发布许可。
- 样本素材（Kei/Epsilon）**严禁商用**（EULA §5.5，仅限内部评估）。文档"MVP 用原创角色"恰好合规，但应写明原因。
- 商标：产品名不得含 "Live2D"（§5.3.1）。

### 3.2 🔴 Expandable Application 触发条件被误判

文档担心"AI 对话/服装/收费方式"触发 Expandable，**归因错位**：

官方定义（EULA §1.5）核心是 **"通过添加或组合文件/数据生成不定数量模型"**。

| 文档担忧                     | 实际评估                              |
| ---------------------------- | ------------------------------------- |
| "AI 对话"触发                | **过度担心**，与 §1.5 无关            |
| "收费方式"触发               | **过度担心**，收费只决定走 Plan D/F/G |
| "无限换装"触发               | **担心不足**——这才是真正灰区          |
| "任意导入/角色商店/插件"触发 | **准确**                              |

### 3.3 🔴 换装实现方式决定许可归类（全文最关键判断）

| 换装实现方式                   | 是否触发 Expandable  | 依据                                         |
| ------------------------------ | -------------------- | -------------------------------------------- |
| ① 每套服装=独立完整 .moc3 文件 | **可能触发** §1.5(a) | "adding files to generate indefinite models" |
| ② 服装=同一模型部件/纹理切换   | **大概率不触发**     | 模型数始终=1，走标准 Plan G                  |
| ③ 独立模型文件+运行时拼接      | **明确触发**         | "combining files or data"                    |

**结论**：若坚持"单一原创角色 + 部件级换装（方式②）"，归普通 SDK 许可，非 Expandable。文档把"MVP 不开放导入"当作规避 Expandable 的充分条件是**判断不完整**——真正决定性因素是换装实现方式。

### 3.4 🟠 Small-Scale 下免费但仍须签约

- 公司年销售额 < ¥1000 万 → Small-Scale，所有 Plan 费用为 **Free**
- 但"免许可费"≠"免签约"——**发布前仍须签 Publication License Agreement**，且须提前至少 1 个月启动
- 营收预警阈值：接近 ¥1000 万时触发法务复审（升 Middle-Scale 开始付费）

### 3.5 备选方案（若 Live2D 许可不可接受）

| 方案         | 许可                               | 表现力                    | 适配度       |
| ------------ | ---------------------------------- | ------------------------- | ------------ |
| **Spine 2D** | Runtime 免版税，无 Expandable 概念 | 弱于 Live2D（无网格形变） | 首选替代     |
| E-mote（M2） | 按平台收费，无免费豁免             | 接近 Live2D               | 成本固定较高 |
| DragonBones  | MIT 免费                           | 中等，已停更              | 工具链风险   |

## 四、后端与实时通信（设计稿第 9 章）

> 总评：架构方向扎实正确（事务即真相、Realtime 仅通知、可靠性分级、幂等+inbox_seq 补偿），无原则性错误。主要问题是对 Supabase 限制与计费量化不足。

### 4.1 🔴 Pro 档 500 并发连接是硬上限（重大遗漏）

文档假设封测 500-1000 MAU 可在 Pro 跑，但 **Pro 档 500 并发连接是硬技术上限**（非计费配额），超过会 `too_many_connections` **拒绝新连接**。

桌宠是"常驻桌面"产品，并发率天然高。1000 MAU 在线峰值 40-60% 即达 400-600，封测期就可能撞顶。

**修订**：9.1/12.6 必须加"Pro 500 并发为硬上限；预期峰值接近时须关 spend cap 进入 10,000 档（仍按 $10/1000 计超额），设并发连接告警"。

### 4.2 🟠 Presence 计费未量化（隐藏成本黑洞）

Presence 心跳本质是 Broadcast 同步。500 常驻用户若每 10 秒同步，理论月消息量可达**亿级**，把 Realtime 消息费推到 $3000+/月。

**修订**：PoC 阶段必须实测 Presence 真实计费量，成本表单列。第 16 节验收清单增加此项。

### 4.3 🟠 补偿机制两个边界未写

inbox_seq 补偿逻辑自洽，但缺两个边界：

1. **`/sync` 分页策略与返回上限**：文档只写 `afterInboxSeq`，没写单次返回上限、游标推进、过期事件处理。建议补"单次最多返回 N 条（如 200），客户端循环调用；B 类短期事件过期后服务端直接推进游标不返回"。
2. **Broadcast Replay 72 小时窗口**：仅当消息从数据库函数发出才持久化，**最多保留 72 小时**。超过只能走 `/sync`。应区分"Broadcast Replay（72h 快速路径）"与"`/sync`（A 类永久慢路径）"。

### 4.4 🟠 Supabase Auth 单设备撤销有 JWT 滞后

`signOut({scope:'others'})` 撤销 refresh token，但 access token **过期前仍有效**（几分钟~1小时）。文档"立即停用旧设备"光靠 Auth 不够。

**修订**：9.8 明确"Auth 撤销 + 应用层 `active_display_device_id` 校验双保险；access token TTL 设短（如 15 分钟）"。

### 4.5 🟡 其他优化点

- **pgvector 判断正确**，1000 MAU 规模完全够用，无需改。建议补"记忆表按 owner_user_id 建部分索引 + HNSW + halfvec"。
- **P2P 排除理由略绝对**：异步链路排除 P2P 正确，但 P1 实时双宠动作同步（<100ms）可评估 WebRTC DataChannel 作为**附加**实时通道（仅传动画意图，业务真相仍走服务端）。
- **Cloudflare Durable Objects** 可作为 P1 成本优化项（文档引用了但没用）；当 Realtime 连接成本超阈值时评估迁移收件箱。
- **RLS 性能**：策略必须只引用索引列 + `auth.uid()`，禁止跨表子查询。
- **Edge Function 冷启动**：高频低延迟事件直接走 Broadcast，不经 Edge Function。

## 五、法规与合规（设计稿 11.10、13.x）

> 总评：框架态度对（先评估再开放、靠 Allowlist），但**两处实质性低估**（美国、中国内地）和**多处表述不精确**。

### 5.1 🔴 中国《拟人化互动服务办法》（2026-07-15 施行，文档完全遗漏）

五部门联合，与 AI 社交陪伴产品**直接相关**：

- 严禁向未成年人提供虚拟伴侣/虚拟亲属
- 连续使用 2 小时**防沉迷**
- 强制"非真人"显著提示
- 整治情感诱导

文档第 2 章（市场）和第 11 章（合规）都未提及。若产品拟在中国发行，必须内置防沉迷、年龄识别、非真人提示、情感诱导合规。

### 5.2 🔴 中国内地门槛被低估

文档说"未完成评估前不向内地提供注册"，方向对但**不充分**：

| 真实门槛                                               | 文档是否提及                       |
| ------------------------------------------------------ | ---------------------------------- |
| 算法备案（生成合成类）+ 安全评估（上线前申报）         | 提了"算法"，未点明触发条件         |
| **境内实体 + ICP 备案/许可**                           | ❌ 完全未提（真正阻塞项）          |
| **境内提供者不得接入 OpenAI/Anthropic 等境外 API**     | ❌ 完全未提                        |
| AI 内容标识（2025-09-01 已生效，须 P0 实现）           | 列为"评估项"，未落实为实现项       |
| 数据出境三路径（安全评估/SCC/认证，**不存在白名单**）  | "不发给未批准境外供应商"表述不精确 |
| **封测不豁免备案**（100-300 人可能达"向公众提供"门槛） | ❌ 未覆盖封测阶段                  |

**关键结论**：MVP 默认排除中国内地（含封测），除非完成境内实体设立+备案+安全评估+内容标识+合规境内模型链路——4-6 个月 MVP 内无法完成。

### 5.3 🔴 美国 NY/CA 已生效专门法（文档最大盲区）

文档把美国写成"按州评估"，但 2025 年已有两部**专门针对 AI companion 的硬性法律**：

| 法律            | 生效                 | 核心义务                                                                                   | 罚则                  |
| --------------- | -------------------- | ------------------------------------------------------------------------------------------ | --------------------- |
| **纽约 A6767**  | 2025-11-05 已生效    | 对**所有用户**（含成年）：会话开始+每 3 小时 AI 披露；危机协议引导至危机服务；不得鼓励自伤 | 每日最高 $15,000      |
| **加州 SB 243** | 核心 2026-01-01 生效 | 知道是未成年人时：每 3h 休息提醒、防性内容；自杀/自伤协议须**官网公布**                    | 私人诉权，每项 $1,000 |

**与文档冲突点**：文档 11.8 危机流程"不公开协议详情"与加州"须官网公布"**冲突**，需修正。文档"按州评估"已不足以描述现状——开放 NY/CA 就已适用，是硬性义务而非评估项。

### 5.4 🟠 18+ 自我声明在多地区已不够

文档 11.6"只有自我声明足够的地区才开放"，但：

- **英国 Ofcom 明确不接受自我声明**，2026-01 已对 companion 服务商 Novi Ltd 启动年龄核查调查
- **韩国**对有害青少年内容须 i-PIN/手机实名年龄核验
- **日本**年龄义务化正在推进

**对首发地区的影响**：优先选当前接受自我声明的地区（NY/CA/欧盟主要国/日本），明确排除英国（除非接入 Yoti 等年龄核验）和韩国。

### 5.5 🟡 其他合规点

- **EU AI Act**：Article 5 操纵禁令**2025-02-02 已生效**（文档措辞像"未来"）；本产品因不采集用户生物特征情绪，通常**不触发** Annex III 高风险（须写清此判断）。
- **应用商店 AI 披露**：苹果 Guideline 5.1.2(i)、Steam AI Content Survey——官网分发可规避，但一旦上架 Steam/MAS 须遵守。
- **未成年人误入检测**：文档仅"注册确认 18+"，缺运营中检测→降级机制（NY/CA"知道是未成年人"即触发）。
- **多人数据处理**：好友共同养宠涉及多方同意，羁绊记忆"双方同意"设计良好但缺法律定性。

## 六、成本与发行（设计稿第 12、13 章）

> 总评：框架和排除项清单健全，方向正确。主要问题是部分数字偏乐观 1.5-3 倍，以及两个发行陷阱未写明。

### 6.1 🟠 AI 单位成本偏乐观

文档目标 $0.35-0.70/月（中等活跃）。按 2026-08 实际定价反推：

| 路由策略                                      | 中等活跃月成本 | 重度月成本 |
| --------------------------------------------- | -------------- | ---------- |
| 全程最低档（GLM-4-Flash免费 + DeepSeek-V3.2） | $0.10-0.20     | —          |
| gpt-4.1-mini 全链路（含双审核走付费模型）     | $0.30-0.50     | $2-5       |
| 中等档混合（Sonnet/Haiku 主对话，L2 场景）    | **$0.80-1.50** | $3-6       |

**关键修正**：

- $0.35-0.70 仅在"全程最低档 + 双审核走免费 Moderation"时可达，偏下限
- 一旦记忆融合对话（L2）占比高，现实区间 $0.80-1.50/月
- **核心警告**：文档要求"输入审核+输出审核都调模型"，若审核也走 GPT-4.1-mini 而非免费 Moderation，成本翻倍。**审核必须固定到 OpenAI Moderation（免费）或国产规则引擎，绝不能与对话同档**。

> 建议改 12.5：中等活跃 $0.50-1.50/月，重度 $2-6/月。

### 6.2 🟠 封测基础设施 $155 下限不成立

文档 $155-950/月。实际封测 500-1000 MAU：

- Supabase Pro $25/月足够（**勿默认 Team $299**）
- 遗漏项：事务邮件 $20-80、对象存储+CDN $5-50、Sentry $26-80、域名/监控 $15-40、**税（增值税/销售税/跨境预扣税）**

**建议改为 $80-500/月（不含 AI token）**，AI token 单列。

### 6.3 🟠 Windows EV 证书陷阱（文档未写明）

自 **2023-06-01** 起，CA/B Forum 强制 **EV 代码签名证书私钥须存 FIPS 140-2 硬件**（USB Token/HSM）：

- **EV 才能 SmartScreen 立即通过**，OV 有信誉积累期（新发布者会撞 SmartScreen 警告，影响封测转化）
- 预算 **$300-700/年**（含 USB Token）
- 推荐方案：**云签名（eSigner/Certum Cloud/Azure Key Vault）** 免物理 Token，CI/CD 友好，年费 ~$349-459，对 2-4 人跨平台团队最优

> macOS 章节（$99/年含全部）准确无遗漏。

### 6.4 🟡 定价低于行业

| 竞品              | 月费       |
| ----------------- | ---------- |
| Replika Pro       | $19.99     |
| Character.AI Plus | $9.99      |
| 文档建议          | $4.99-7.99 |

封测验证价合理（低价测转化），但**正式上线建议 $7.99-12.99/月**。¥25-45/月 中国档比汇率等值低 ~30%，属合理本地化，但须做地区锁防套利。

### 6.5 Steam 抽成影响（印证"后续评估"正确）

Steam 30% 抽成使 $4.99 订阅实得 $3.49；官网直发仅信用卡费 ~8%。**订阅型产品官网分发毛利优势明显**，印证文档"Steam 后续评估"决策正确。
