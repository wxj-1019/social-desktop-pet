## 一、D 阻断类决策

### D-1 首发测试地区与简体中文优先的落地方案 🔄

- **问题**：MVP 封测的 100–300 名测试者实际来自哪个地区？
- **背景**：设计稿 6.1 与 13.5 规定 MVP 只覆盖简体中文；11.10 规定中国内地须完成专项评估才开放。第二轮调研（[调研发现 §5](../2026-08-01-research-findings.md)）发现原 a/b/c 选项过于笼统，应基于各地**实际合规门槛**重新划分：
  - **中国内地**：须境内实体 + ICP + 算法备案 + 安全评估 + AI 内容标识（2025-09-01 已生效）+ 禁境外 API + 封测不豁免备案。**4–6 个月 MVP 内无法完成，应明确排除**。
  - **英国**：Ofcom 明确不接受自我声明年龄核验，2026-01 已对 companion 服务商启动调查。**不建议 MVP 首发，除非接入 Yoti 等年龄核验**。
  - **韩国**：对有害青少年内容须 i-PIN/手机实名年龄核验。**不建议 MVP 首发**。
  - **纽约州**：A6767 已于 2025-11-05 生效，对所有用户要求 AI 披露 + 每 3h 周期通知 + 危机协议。可候选但须 P0 实现这些义务。
  - **加州**：SB 243 核心 2026-01-01 生效，危机协议须官网公布 + 未成年人保护。可候选但须 P0 实现。
  - **欧盟主要国**：非色情 18+ 陪伴产品自我声明当前可接受；Article 5 反操纵已生效（文档已满足）。可候选。
  - **日本**：自我申报当前占主导，年龄义务化在推进。可谨慎候选。
- **影响**：决定法务工作量、测试者招募渠道、留存结论的可外推范围、P0 合规功能清单（危机协议/披露频次/年龄核验）；直接影响第 1–2 周 PoC 与第 15–18 周封测的启动条件。
- **选项**（已按调研发现重写）：

| 选项 | 方案                                                          | 优点                                                 | 风险                                                                                                  |
| ---- | ------------------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| a    | **NY + CA + 欧盟主要国 + 日本** 候选组合，界面保持简中        | 合规路径可行，按时启动封测；覆盖主要 AI 陪伴消费市场 | 测试者画像与目标用户（简中泛二次元）存在偏差，留存结论外推受限；需实现 NY/CA 的 P0 合规义务（见 V-8） |
| b    | a 之上叠加**港澳台/海外华人圈**定向招募，强化简中目标用户浓度 | 兼顾合规与目标画像                                   | 港澳台须复核本地规则；招募成本上升                                                                    |
| c    | 维持原"内地评估先行"                                          | 测试者与目标画像一致                                 | 内地合规周期 6+ 个月，**大概率推迟 MVP 整体节奏至不可接受**                                           |

- **建议**：选 a（或 a+b 组合）。明确排除中国内地与英国出 MVP。此决策依赖执业律师对各州/国适用性的书面确认（见 V-3）。

### D-3 记忆确认交互的触发形态 🔄（整合 D-10）

- **问题**：6.2 规定持久记忆默认需用户逐条确认，但"每条候选记忆都弹确认卡"可能造成高频打扰，反而降低确认率。
- **背景**：15.3 要求 ≥50% 用户"理解并操作一次记忆确认"；10.6 规定候选记忆需审核与来源。确认卡触发的频率与形态目前未限定。**第二轮调研补充关键证据**（[第二轮调研 §1.4、§4.5](./2026-08-01-research-findings-round2.md)）：
  - **四大家（ChatGPT/Claude/Character.AI/Replika）全部"自动写入 + 事后管理"，无一逐条确认**。用户信任来自"可见性 + 可撤销性"，而非前置打断。
  - 确认卡在业界**没有成熟参照实现**，"≥50% 用户理解并操作"是未经任何产品验证的指标，无基准可循。
  - 但确认制与 OWASP LLM01 的 human-in-the-loop 安全要求一致，且"可治理记忆"是仅剩的差异化护城河之一——不宜完全放弃，应分级。
- **影响**：直接影响核心留存体验与 15.3 指标达成，需要同步修订 6.2、10.6 和 AI 评测集（13.5）中的对应用例。
- **选项**：

| 选项 | 方案                                                                                                                                                                                          | 优点                                                | 风险                                                      |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- | --------------------------------------------------------- |
| a    | **分级确认**（推荐）：敏感/高影响事实（健康、财务、亲密关系、身份）→ 保留 6.2 确认卡；普通偏好 → 自动保存 + 轻量"已记住·撤销"提示 + 记忆中心批量复核；onboarding 第一张卡做成教学卡、单键确认 | 兼顾安全差异化与低打扰；与业界"自动+事后管理"不冲突 | 需要实现敏感度分类与记忆中心批量复核（P0 工作量小幅增加） |
| b    | 全部弹卡：字面执行 6.2                                                                                                                                                                        | 实现简单、语义一致                                  | 高频打扰；业界无此做法，与"养成陪伴"流畅体验相悖          |
| c    | 全自动 + 事后管理面板：完全对齐四大家                                                                                                                                                         | 打扰最低、实现最简单                                | 放弃"可治理记忆"差异化；敏感事实可能被自动记录            |
| d    | 首次强引导 + 后续低打扰：首次使用流程强制演示一次确认，之后按 a 执行                                                                                                                          | 引导与长期体验兼顾                                  | 需要组合实现                                              |

- **建议**：选 a（分级确认），可叠加 d（首次教学卡）。指标口径收紧为"**看到确认卡的用户中 ≥50% 完成一次确认/修改**"（分母是见到卡的人，非全体安装用户），并在首次确认后当场展示记忆中心入口（否则 15.4"1 分钟找到删除入口"过不了）。
- **结论**：□ a　□ b　□ c　□ a+d　□ 其他：____________________

### D-4 好友绑定留存验证的判定口径 🔄

- **问题**：15.3 要求"绑定用户 D7 留存比未绑定用户高至少 10 个百分点"。第二轮调研（[第二轮调研 §2.2](./2026-08-01-research-findings-round2.md)）确认两个硬伤：**①统计功效不足**——300 人封测按 30–40% 绑定率（绑定组~~100、未绑定组~~200），检测下限约 **20pp**，测不出 10pp（需每组~356 人）；**②选择偏差**——愿意邀请的用户本身高意向，即使绑定无因果效果，绑定组留存也必然更高（业界观察的 2–3 倍差距大头是选择偏差，不是因果）。
- **背景**：好友绑定能否提升留存是全文最大商业未知（0.4），也是核心 Go/No-Go；样本量不足 + 选择偏差并存时，纯相关性对比无论结果如何都不可信。
- **影响**：决定封测结束后如何下结论，以及第 19–24 周的决策依据。实验设计选择见 D-12。
- **选项**（数值口径）：

| 选项 | 方案                                                                                                               | 说明                                                                         |
| ---- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| a    | **+15pp 或相对提升 ≥1.5 倍** + 实验排除选择偏差（D-12）+ 前置门禁"未绑定激活用户 D30 ≥8%（AI companion 品类下限）" | 可检测（300 人测 15pp 需每组~128 人）+ 与行业相对提升同口径 + 单人循环先成立 |
| b    | 扩大封测样本至 500+ 以追求 10pp 统计显著                                                                           | 封测规模与成本上升，招募与运营压力大                                         |
| c    | 维持 10pp + 辅助证据（访谈、漏斗行为）综合判定                                                                     | 统计上不可测，综合判定仍是"看感觉"                                           |

- **建议**：选 a。修订点：
  1. 阈值 "+10pp" → "**+15pp 或相对 ≥1.5 倍**"；
  2. 必须配合 D-12 的实验设计排除选择偏差，不能仅凭相关性 Go；
  3. 新增前置门禁"**未绑定激活用户 D30 ≥8%**"——若单人循环留不住人，绑定实验无意义（Molili 关停教训）；
  4. 若观测差距 <2 倍相对值，用 D-12 的鼓励实验区分因果与选择偏差。
- **结论**：□ a　□ b　□ c　□ 其他：____________________

### D-7 逐像素穿透不可达与 MVP 卖点折损 🆕

- **问题**：设计稿 8.4 承诺"MVP 只支持整窗穿透切换"。第二轮调研（[调研发现 §2.2](../2026-08-01-research-findings.md)）确认 Electron **原生不支持**透明区域点击穿透（官方文档明示，issue #1335 至今未关）。唯一可用方案是 `setIgnoreMouseEvents(true,{forward:true})` + 渲染进程 JS 探测光标下 alpha 切换，存在**可观察的体验折损**（边缘抖动、拖拽经过宠物误判、点击身后窗口需先移开）。是否接受这一折损，直接影响"桌宠常驻不妨碍工作"这一核心卖点的成立。
- **影响**：若不接受，需要重新评估客户端路线（自研原生壳层 / 接受 Tauri 结构性缺口 / 调整产品形态）；若接受，需在设计稿产品章节明确标注此限制，避免用户预期落差。
- **选项**：

| 选项 | 方案                                                                                                      | 优点                           | 风险                                                    |
| ---- | --------------------------------------------------------------------------------------------------------- | ------------------------------ | ------------------------------------------------------- |
| a    | 接受折损，MVP 维持整窗穿透；在产品章节明确标注"逐像素无感穿透不可达"，并在 UI 提供便捷的手动切换/托盘恢复 | 不阻塞 Electron 路线，按时交付 | 核心卖点有体验折损，可能影响封测留存结论（与 D-4 交织） |
| b    | 在第 1–2 周 PoC 实测整窗穿透 + alpha 探测方案的真实体验，**以实测结果决定是否接受**                       | 决策基于真实数据而非文档判断   | PoC 多一项关键验证，但这是必须做的                      |

### D-8 服装系统实现方式与 Live2D 许可归类 🆕

- **问题**：设计稿 0.2-8 与 8.8 规定"MVP 只内置一个原创角色，不开放任意模型导入"，并担忧"无限换装"触及 Expandable Application 许可。第二轮调研（[调研发现 §3.3](../2026-08-01-research-findings.md)）发现：**是否触发 Expandable 取决于换装实现方式，而非是否开放导入**。
- **背景**：Live2D EULA §1.5 的核心触发条件是"通过添加或组合文件/数据生成不定数量模型"。三种实现方式：
  - 方式①：每套服装 = 独立完整 .moc3 文件 → **可能触发** §1.5(a)
  - 方式②：服装 = 同一模型的部件/纹理切换（模型数始终 = 1）→ **大概率不触发**，走标准 Plan G
  - 方式③：独立模型文件 + 运行时拼接 → **明确触发**
- **影响**：此决策决定（1）是否需要走 Expandable 专项许可（影响成本与 Live2D 书面确认周期，见 V-1）；（2）美术资产的制作规范（部件级换装 vs 整模型换装，影响建模工作量）；（3）P1"更多原创服装"功能（12.4）的实现路径。
- **选项**：

| 选项 | 方案                                                                     | 优点                                                                       | 风险                                                                |
| ---- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| a    | **采用方式②**：服装统一为同一 .moc3 的部件/参数/纹理切换，模型数始终 = 1 | 大概率规避 Expandable，走标准 Plan G（Small-Scale 下免费）；美术资产复用高 | 部件级换装对建模要求高；复杂服装（如整体换风格）难用部件实现        |
| b    | 采用方式①：每套服装独立模型文件                                          | 建模灵活，可整体替换风格                                                   | 可能触发 Expandable，需专项许可 + Live2D 书面确认，周期与成本不确定 |
| c    | 待 V-1（Live2D 书面确认）结果再定                                        | 决策基于官方裁定                                                           | 阻塞美术资产生产，可能拖延第 3–6 周单人 Alpha                       |

- **建议**：选 a。这是唯一能同时满足"规避 Expandable + 不依赖书面确认即可开工 + Small-Scale 免费"的方案。即便 Live2D 后续书面裁定方式②也需专项许可，Small-Scale 下费用仍为 0。设计稿 8.8 应写死此技术约束。

### D-9 封测并发连接预算与 Supabase 套餐 🆕

- **问题**：设计稿 12.6 假设封测 500–1000 MAU 可在 Supabase Pro 跑。第二轮调研（[调研发现 §4.1](../2026-08-01-research-findings.md)）发现 **Pro 档 500 并发连接是硬技术上限**（非计费配额），超过会 `too_many_connections` **拒绝新连接**。桌宠是常驻桌面产品，并发率天然高于普通 Web 应用。
- **背景**：1000 MAU 在线峰值 40–60% 即达 400–600 并发，封测期就可能撞顶。撞顶后新登录用户被拒连，直接影响封测可用性。解决方案是关闭 spend cap 进入 10,000 连接档（仍按 $10/1000 峰值连接计超额），但这会引入不可预测的超额成本。此外 Presence 心跳可能是隐藏的成本黑洞（见 V-10）。
- **影响**：决定（1）封测是否一开始就关 spend cap；（2）封测规模上限（500 还是 1000）；（3）月度成本预期（是否需要从 $80-500 上调）；（4）是否需要在 PoC 阶段评估 Cloudflare Durable Objects 作为收件箱替代（见调研发现 §4.5）。
- **选项**：

| 选项 | 方案                                                                                               | 优点                             | 风险                                                          |
| ---- | -------------------------------------------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------- |
| a    | 封测规模保守定为 500 MAU，维持 Pro + spend cap                                                     | 成本可控，500 并发内大概率不撞顶 | 测试样本量小，D-4 留存判定更难显著                            |
| b    | 封测规模维持 1000 MAU，但**从一开始就关 spend cap**（进 10,000 连接档）                            | 不撞顶，支持预期规模             | 月成本不可预测（Presence + 连接超额），需 V-10 实测后回填预算 |
| c    | 封测规模 1000 MAU，并在 PoC 阶段同步评估 Cloudflare Durable Objects 作为收件箱（长连接几乎不计费） | 长期成本最优                     | 增加架构复杂度，2–4 人团队额外工作量                          |

- **建议**：选 b。封测期保留规模弹性比省成本重要（D-4 需要样本）。但**必须**在第 1–2 周 PoC 完成 Presence 实测（V-10）并据此回填 12.6 成本区间。若 Presence 计费失控，再评估 c。
- **结论**：□ a　□ b　□ c　□ 其他：____________________

### D-12 "绑定提升留存"验证方案 🆕

- **问题**：D-4 定了判定阈值（+15pp 或相对≥1.5 倍），但**如何排除选择偏差**还需选定实验方法。纯"绑定组 vs 未绑定组比 D7"是纯相关分析——愿意邀请的用户本身高粘性，即使绑定无因果效果，绑定组留存也必然更高。
- **背景**：第二轮调研（[第二轮调研 §2.2](./2026-08-01-research-findings-round2.md)）指出，业界观察到的绑定/未绑定 2–3 倍差距里大头是选择偏差而非因果。设计稿 15.3 目前是纯相关对比。
- **影响**：决定 Go/No-Go 结论的可信度——若不能区分因果与选择偏差，"绑定不提升留存就停止联机建设"的止损条款无法可信执行。
- **选项**：

| 选项 | 方案                                                                                                                                                                                | 优点                                                           | 风险                                                             |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------- |
| a    | **鼓励实验（Encouragement RCT）**：随机化"邀请提示的曝光强度"（实验组 D1/D3 高曝光引导，对照组弱曝光）。提示随机分配与绑定相关、与留存只通过绑定相关，构成工具变量。报告 ITT + LATE | 业界标准做法；不剥夺任何用户功能，只随机化提示强度，伦理可接受 | 需在封测埋点中实现随机分组 + ITT/LATE 报表（后端工作量小幅增加） |
| b    | 未接受邀请对照组：比较"发出邀请但未被接受" vs "被接受"的用户。两组都自选了"愿意邀请"，选择偏差大幅抵消                                                                              | 零成本自然实验，埋点即可                                       | 依赖"对方是否接受"近似外生的假设；样本可能不足                   |
| c    | 倾向得分分层：用绑定前行为分层后比较                                                                                                                                                | 至少剔除"绑定前已表现出的粘性"                                 | 无法排除未观测到的混杂；严禁用绑定后行为匹配（对撞偏差）         |
| d    | 纯相关分析（维持设计稿现状）                                                                                                                                                        | 最简单                                                         | 结论不可信，Go/No-Go 无法据此执行                                |

- **建议**：选 a（鼓励实验）为主，b（未接受对照组）为辅。c 可作补充。**不建议 d**——这会让核心 Go/No-Go 失去意义。需要在封测埋点中实现随机分组字段与 ITT/LATE 报表。
- **结论**：□ a　□ b　□ a+b　□ c　□ d　□ 其他：____________________
